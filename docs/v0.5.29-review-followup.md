# v0.5.29 release review follow-up

The implementation below replaces the pending release checklist. The first gate's automatic acceptance did not authorize retaining these defects. Existing gate-fix commits remain intact. The integration base is `a07552340d9ca11dfe9ca4b8fea7523c6b7f586d` on `v0.5.x`.

## Implemented corrections

1. **Local-device recovery.** Metadata-attached disks now stop with an actionable manual-repair report. The automatic recovery path contains no detach operation. Direct same-node attach requires typed inspection identifying the expected image and node with no VM owner or disk record. Lookup errors and unavailable inspection fail closed, including provider attach retries. The VM must appear in the successful attachment inspection; contradictory image usage and missing targets cannot authorize a retry. The controller commits `hotplug_in_progress` before attachment. Provider completion follows the conditional transition described below. Filesystem NodeStage and raw-block NodePublish capture their reports before observing the device. Confirmation and deletion compare that observed episode on every conflict retry, preserving newer reports and removals. A timed-out operation that never recorded completion remains manual-repair work; node visibility alone cannot certify its completion. No force flag authorizes an automatic detach.
2. **CephFS ownership reconstruction.** Both NodeStage and NodePublish discover all mounted CSI targets using adjacent kubelet metadata before saving a missing session. Discovery works with an absent stage and disconnected binds on an older superblock. Session validation retains mount-identity checks, rejects ambiguous mounts and other-volume ownership, and preserves read-only and security flags. Recovery receives both sibling targets before FUSE invocation. Sibling target metadata detects conflicting ownership even when both stages are absent; healthy or unknown-health retained binds prevent cleanup and remount. Tests also assert that an unrelated volume's mounts are unchanged.
3. **Hotplug snapshot persistence.** Per-node workers perform Kubernetes writes outside the global bookkeeping lock. Queue admission and cancellation do not wait for diagnostic persistence. Versions assigned while queue state is locked reject delayed older snapshots. A worker serializes each node's writes and caches only successful, current writes. Kubernetes resourceVersion preconditions reject an old server-side write that survives a client timeout and arrives after a newer snapshot. Completion clears bypass debounce. Requests have two-second deadlines and failed writes receive up to five delayed retries at 100, 200, 400, 800 and 1600 milliseconds. After exhaustion, the latest snapshot remains available for a later queue update to retry; this is a bounded retry policy, not unlimited outage recovery.
4. **Durable repair and history.** Runtime-attachment repair is derived from the terminal local-device report and its episode token. There is no second marker commit that can fail or arrive after confirmation. A failed terminal-report write leaves the pending report eligible for the next sweep; successful confirmation removes the derived repair in the same durable state transition. Legacy standalone runtime markers follow the conditional node-verification protocol below; attempts to publish new standalone runtime markers are rejected. Report-only wrong-identity faults also block both guards. Other repair classifications remain separate. Staging captures repair authority before device verification and conditionally retires only that record; a changed or unreadable report or repair record returns Unavailable for kubelet retry. Provider success cannot retire node-local repair authority. Publish and queue guards fail closed on read errors. History mutations still merge with the latest persisted record using conflict checks; per-volume write ordering keeps Kubernetes I/O outside the shared cache mutex and supports canceled lock waits.
5. **Forced reprobe.** See the [node-side reprobe procedure](../helm/opennebula-csi/DEBUGGING.md#8-supported-node-side-unstage--reprobe) for current annotation requirements, failure handling and consumer coordination.
6. **Benchmark admission.** Node-health admission runs before creating benchmark resources. Existing owned PVC or Job resources for the current generation establish admission after controller restart, including a crash before status persistence. Adding the benchmark's eighth attachment therefore cannot fail its own admission check. The existing job result and cleanup paths continue to run.

A wrong-identity report without existing recovery authority uses `confirmed_by_node` to describe device visibility, which is not successful recovery. Its update callback preserves an existing operation token, completion method/state, deadline, attachment state and metadata on every conflict retry, including episodes begun during physical observation. Ordinary discovery misses and mount failures now retain its classification, identities and recovery budget. Only a successful terminal confirmation resets a subsequent missing-device observation into a fresh episode. This corrects the overly broad reset added after Oracle's snapshot while preserving its intended fresh-episode behavior.

After a successful attach and final provider lookup, the controller records completion against the same nonempty token, node, volume, first observation, recovery attempt count and attempt start time. This completion-only comparison permits concurrent wrong-identity evidence and deadline transitions, including changes found on a conflict retry. It preserves identity evidence, terminal repair state and separate repair markers. An in-progress report becomes pending; an already terminal report retains its state, deadline outcome and observation while gaining provider completion evidence. A replaced token, changed episode or failed persistence cannot acknowledge completion. Node confirmation and deletion retain their stricter episode comparison and require fresh matching identity through NodeStage or raw-block NodePublish before retiring either authority.

Filesystem expansion follows the [node expansion verification contract](node-expansion.md#verification-contract).

The attachment failure handler now retains the token, confirmation state and deadline once provider execution may have begun, including timeouts, connection failures and failed completion lookups. Deadline expiry moves an unfinished attempt to manual repair. A visible device cannot retire that episode without recorded provider completion. Filesystem NodeStage and raw-block NodePublish share the authority snapshot before device discovery. Raw-block publishing verifies the observed repair identity, conditionally confirms the observed report and retires the observed repair before binding or acknowledging an already-bound target. Unfinished episodes and changed or unreadable authority return retry errors without creating a new bind. Block NodeStage still performs no formatting or mounting; block expansion behavior is unchanged.

Device resolution requires a positive observed serial match whenever the publish context, retained report or cache supplies an expected serial. This applies to cache hits, by-id discovery and both immediate and recovery-loop alias candidates. A by-id name, remembered symlink or udev database entry is not serial evidence. Resolution and final device observation share a kernel serial reader: the candidate must be a block device, its major/minor mapping selects the sysfs device, and its device number and inode must remain unchanged across the read. Virtio uses the kernel `serial` attribute. SCSI uses VPD page 0x80 with a direct-access device type, an exact declared payload length and a nonempty printable serial. Missing, malformed or mismatching current identity fails closed; stale udev values cannot override it. Path invalidation and cache expiry retain the known serial while clearing the cached path and by-id reference. Resolution carries its selected serial through success and failure, so a failed request records cache-derived authority in the existing missing-device report without changing the caller's publish context. Consecutive retries, including a retry after cache loss, therefore retain that authority. Contradictory expected serials also fail closed. Discovery and mount failures retain a report's known serial and expected identity regardless of failure classification. The final physical observation must match the known serial and any retained observed identity before confirmation. Requests without any expected identity keep the legacy discovery behavior. A fresh retry can proceed when the matching device becomes observable.

Repair observations distinguish reports derived in memory from persisted legacy markers without serializing that distinction. Released standalone markers with `evidenceSource=local_device_report` can be retired after verification through NodeStage or raw-block NodePublish. Cleanup compares the observed legacy JSON value again on every conflict retry, so replacement evidence survives even when its timestamps and failure count are unchanged. If both records exist, node verification retires the report first and retries against the remaining legacy marker.

Every snapshot write also changes one annotation per node on the existing diagnostic ConfigMap, using a hashed node key and a unique write token. Even an already-empty clear therefore commits a new resource version. This accounts for [Kubernetes skipping unchanged storage writes](https://github.com/kubernetes/apiserver/blob/v0.32.3/pkg/storage/etcd3/store.go#L478-L500). Resource-version preconditions continue to reject delayed older writes; other nodes' data and annotations are preserved.

CephFS discovery reads CSI metadata before applying OpenNebula ownership validation. A foreign driver with a distinct volume handle and unrelated mount identity is excluded. Foreign metadata sharing the affected stage or a sibling's mount identity, or claiming the affected handle, still blocks reconstruction before any cleanup.

## Challenge reconciliation and rollout contract

The completed same-conversation challenge is `/tmp/csi-v0529/oracle-challenge-result.md`. Follow-up regressions cover the actual NodeStage RPC for in-progress, newly created, advanced and terminalized episodes on new and already-mounted stages; fresh retries finish a completed timed-out episode. Additional cases cover zero unauthorized attach retries, legacy/report-only repair guards, a new fault after physical observation, history-independent retirement, absent-stage ownership/health rejection, and an HTTP request continuing at the API after its client timeout.

Controllers must be upgraded first, after existing hotplug requests and provider operations have settled. Parent context cancellation or a new leader alone does not prove OpenNebula operations stopped. All four clusters use OnDelete node rollout. During controller/node skew, do not initiate recovery of a faulted legacy node; quiesce its affected consumers and replace that node plugin before restaging. Legacy unconditional writers cannot provide the new/new preservation guarantee. Do not roll controllers back while revised nodes remain active. Normal ordered application drain, NodeUnpublish and NodeUnstage remain supported.
