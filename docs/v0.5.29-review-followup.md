# v0.5.29 release review follow-up

The implementation below replaces the pending release checklist. The first gate's automatic acceptance did not authorize retaining these defects. Existing gate-fix commits remain intact. The integration base is `a07552340d9ca11dfe9ca4b8fea7523c6b7f586d` on `v0.5.x`.

## Implemented corrections

1. **Local-device recovery.** Metadata-attached disks now stop with an actionable manual-repair report. The automatic recovery path contains no detach operation. Direct same-node attach requires typed inspection identifying the expected image and node with no VM owner or disk record. Lookup errors and unavailable inspection fail closed. The controller commits `hotplug_in_progress` before attachment, then changes it to `pending_runtime_confirmation` after completion. NodeStage captures its report before observing the device. Confirmation and deletion compare that observed episode on every conflict retry, preserving newer reports and removals. A timed-out operation that never recorded completion remains manual-repair work; node visibility alone cannot certify its completion. No force flag authorizes an automatic detach.
2. **CephFS ownership reconstruction.** Both NodeStage and NodePublish discover all mounted CSI targets using adjacent kubelet metadata before saving a missing session. Discovery works with an absent stage and disconnected binds on an older superblock. Session validation retains mount-identity checks, rejects ambiguous mounts and other-volume ownership, and preserves read-only and security flags. Recovery receives both sibling targets before FUSE invocation. Tests also assert that an unrelated volume's mounts are unchanged.
3. **Hotplug snapshot persistence.** Per-node workers perform Kubernetes writes outside the global bookkeeping lock. Queue admission and cancellation do not wait for diagnostic persistence. Versions assigned while queue state is locked reject delayed older snapshots. A worker serializes each node's writes and caches only successful, current writes. Completion clears bypass debounce. Requests have two-second deadlines and failed writes receive up to five delayed retries at 100, 200, 400, 800 and 1600 milliseconds. After exhaustion, the latest snapshot remains available for a later queue update to retry; this is a bounded retry policy, not unlimited outage recovery.
4. **Durable repair and history.** Runtime-attachment repair is derived from the terminal local-device report and its episode token. There is no second marker commit that can fail or arrive after confirmation. A failed terminal-report write leaves the pending report eligible for the next sweep; successful confirmation removes the derived repair in the same durable state transition. Legacy standalone runtime markers do not independently block recovery, and attempts to publish new standalone runtime markers are rejected. Other repair classifications remain separate and take precedence; successful clearing reads current durable state and conditionally deletes only the observed record. Publish and queue guards fail closed on read errors. History mutations still merge with the latest persisted record using conflict checks; per-volume write ordering keeps Kubernetes I/O outside the shared cache mutex and supports canceled lock waits.
5. **Forced reprobe.** Forcing cleanup with published targets requires current PV/PVC `recovery-mode=manual` and a future `recovery-mode-until`. Historical session mode grants no authority. Missing clients, failed PV/PVC reads, malformed or absent deadlines, expired mode and removed annotations prevent cleanup. Manual mode permits only the existing scoped reprobe; consumers still require deliberate coordination and the automatic detach restriction remains in force.
6. **Benchmark admission.** Node-health admission runs before creating benchmark resources. Existing owned PVC or Job resources for the current generation establish admission after controller restart, including a crash before status persistence. Adding the benchmark's eighth attachment therefore cannot fail its own admission check. The existing job result and cleanup paths continue to run.

The wrong-identity report uses `confirmed_by_node` to describe device visibility, which is not successful recovery. Ordinary discovery misses and mount failures now retain its classification, identities and recovery budget. Only a successful terminal confirmation resets a subsequent missing-device observation into a fresh episode. This corrects the overly broad reset added after Oracle's snapshot while preserving its intended fresh-episode behavior.

Filesystem expansion continues to require full device capacity and successful filesystem geometry verification. Statfs byte values are diagnostic because ext4 metadata reduces them. A statfs syscall failure remains fatal.
