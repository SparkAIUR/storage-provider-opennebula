OpenNebula 7.4 upgrade and qualification

This candidate supports OpenNebula 7.4.x over XML-RPC. The observed target is 7.4.0; the SDK/source contract is pinned to the 7.4.1 line. Go1.27.4, Kubernetes libraries0.36.6, CSI1.13 and the chart0.6.0-rc.1 move together. The qualification targets are Kubernetes1.36 on hpldb and1.35 on hplsvc/bravo; none is accepted by this source work. Local unit, protocol, render, race and container checks do not establish provider or deployment acceptance.

Queue validation and direct prechecks return Unavailable for unknown attachment observations. Only ErrAttachmentNotFound, including wrapped forms, establishes attachment absence. Requested-VM absence may coexist with consistent attachment records on other VMs, allowing approved sticky moves and shared readers. Image usage that contradicts the requested VM or lacks corresponding observed owners remains unknown. Deletion and recovery still require global ownership absence. Capacity restoration and detach sizing select the requested VM disk; restoration keeps terminal resize checks and the existing volume lock. Explicit expansion without a requested VM still rejects ambiguous multiple attachments. Same-node sticky reuse, unpublish rescue, expiry and recovery reattach retain their protective state when a recheck fails; expiry uses one attachment observation. Maintenance held-detach success remains available on its existing verified paths.

Disk operations fail closed on unknown visibility, conflicting ownership, duplicate image names, unresolved quarantine and historical FORCE_DELETE. Durable known image IDs remain pinned during deletion/readback. A successful name-pool query alone cannot establish physical deletion. New disk snapshots and detached disk growth are unavailable, including when old feature flags request them. CephFS is independent. Existing detached image snapshots retain their handles and support observed asynchronous deletion; attached VM snapshot cleanup requires external reconciliation and returns a precise precondition failure.

Attached growth waits for terminal VM/LCM state and cleared RESIZE/SIZE_PREV. CSI_REQUESTED_SIZE_BYTES is written and read back only after completion. Reattach and ordinary publish retries restore that verified capacity even when canonical image size is stale. Attachment lookup remains read-only for detach and reconciliation callers. Ordinary publish restoration, including already-attached retries, runs inside the node queue callback under the same volume lock as ControllerExpandVolume; the lock covers resize and marker read/merge/write/readback. Completed queue observations still require that callback, and a coalesced request without its own verified response returns Aborted. Never detach a legacy expanded volume based only on optimistic SIZE: record provider disk completion and guest/device capacity first. OpenNebula7.4.0 does not contain the7.4.1 LVM metadata correction; do not claim canonical image metadata alone proves physical capacity. Never repair metadata, detach, delete forcibly or clear quarantine as an upgrade side effect.

Clones inherit CSI_IMAGE_ID atomically from the source template. The driver normalizes self and CSI_CLONE_SOURCE_IMAGE_ID together, with ownership and readback checks. Retry after lost acknowledgement reconciles an inherited or already normalized target, checks capacity and selected datastore, and avoids a second clone. Existing targets use their own capacity even if the source has grown since creation; fresh clones validate source limits and the completed target readback. An existing target without provable origin requires operator investigation. Name equality alone is insufficient. Sources outside the existing csi.opennebula.io ownership convention are rejected. Disk clone capacity errors map to CSI OutOfRange, and incompatible or uncertain targets map to AlreadyExists; wrapped errors retain their actionable detail.
