OpenNebula 7.4 upgrade and qualification

This candidate supports OpenNebula 7.4.x over XML-RPC. The observed target is 7.4.0; the SDK/source contract is pinned to the 7.4.1 line. Go1.27.4, Kubernetes libraries0.36.6, CSI1.13 and the chart0.6.0-rc.1 move together. The qualification targets are Kubernetes1.36 on hpldb and1.35 on hplsvc/bravo; none is accepted by this source work. Local unit, protocol, render, race and container checks do not establish provider or deployment acceptance.

Disk operations fail closed on unknown visibility, conflicting ownership, duplicate image names, unresolved quarantine and historical FORCE_DELETE. Durable known image IDs remain pinned during deletion/readback. A successful name-pool query alone cannot establish physical deletion. New disk snapshots and detached disk growth are unavailable, including when old feature flags request them. CephFS is independent. Existing detached image snapshots retain their handles and support observed asynchronous deletion; attached VM snapshot cleanup requires external reconciliation and returns a precise precondition failure.

Attached growth waits for terminal VM/LCM state and cleared RESIZE/SIZE_PREV. CSI_REQUESTED_SIZE_BYTES is written and read back only after completion. Reattach restores that verified capacity even when canonical image size is stale. Never detach a legacy expanded volume based only on optimistic SIZE: record provider disk completion and guest/device capacity first. OpenNebula7.4.0 does not contain the7.4.1 LVM metadata correction; do not claim canonical image metadata alone proves physical capacity. Never repair metadata, detach, delete forcibly or clear quarantine as an upgrade side effect.

Clones inherit CSI_IMAGE_ID atomically from the source template. The driver normalizes self and CSI_CLONE_SOURCE_IMAGE_ID together, with ownership and readback checks. Retry after lost acknowledgement reconciles an inherited or already normalized target, checks capacity and selected datastore, and avoids a second clone. An existing target without provable origin requires operator investigation. Name equality alone is insufficient. Sources outside the existing csi.opennebula.io ownership convention are rejected.

Candidate publication uses the protected csi-candidate-publication environment and only RC tags. It builds once and produces source/image/chart checksum assets; it never publishes stable artifacts. Do not publish during local implementation work.

Freeze candidate JSON containing sourceCommit, sourceTree, chartVersion, all container image references at @sha256, resolvedImageDigests (architecture children obtained from those exact OCI indices), clusterUIDs, nodeRevisions (raw pod controller-revision-hash, without DaemonSet prefix), and recorded quarantineExceptions. Use actual readback; never invent identities. Bind source/image assets to the candidate release and preserve their SHA256SUMS. The driver, inventory, preflight and reconcile jobs must share the driver digest. Include every sidecar, including optional snapshotter when enabled.
3. Review the isolated spark-kops preparation. It deliberately suspends the three HelmReleases until exact digest patches and approvals exist. Keep snapshotter disabled because these clusters have no snapshot CRDs. Do not install CRDs or alter existing StorageClasses to satisfy the candidate. Keep OnDelete, waits enabled, and no automatic remediation, rollback or cleanup. Other shared infrastructure consumers are outside this rollout.

The former broad lab installers now require an isolated disposable-cluster approval, explicit node/cluster UID and image digest. They change maintenance state and StorageClasses and are unsuitable for hpldb. Their failed resources are retained. The staging workflows cannot turn those installers into production qualification.

Native sequence: hpldb first, hplsvc second, bravo third. Use a unique disposable namespace and PVCs against approved existing StorageClasses. Record create/delete, attach/detach, attached growth plus ordinary reattach with provider/device capacity proof, clone lost-response/retry, CephFS recovery, lookup faults and preserved quarantines. Do not disturb database workloads or use production volumes for fault injection. New disk snapshot/detached-growth rejection is also a required native negative check. Record the actual OpenNebula version, datastore/bridge state, source image IDs, RPC outcome, VM/disk IDs and guest capacity. Unknown cleanup is a failure. Stop and preserve evidence instead of replaying an uncertain mutation.

Keep the normal Helm reconciliation active. Its node-count budget is T=30m*(N+2): hpldb150m, hplsvc360m, bravo450m; parent Kustomization165m/375m/465m. A separate supervised terminal handles one node at a time:

2. Inspect host, plugin and consumer mount/process namespaces. Capture exact commands, namespace IDs and SHA256 of their output. Prove no FUSE mounts/processes or references remain, while preserving kernel mounts/VM attachments. A single findmnt view cannot prove all namespace ownership. If anything remains or is ambiguous, stop for operator repair.

4. Run `python3 hack/supervise_rollout.py --context hpldb --node NODE --candidate candidate.json --drain drain.json` first. Review its UID-bound action. Add --execute only under the specific approved one-node replacement. The tool checks cluster/template/pod custody and consumer absence, issues a nonforced API delete with UID precondition, and performs one bounded wait. It never stops consumers, detaches disks, repairs mounts, retries, rolls back or cleans failed resources.
5. Verify the replacement pod UID, raw revision hash and exact architecture-resolved image digest; verify CSINode driver registration and disposable read/write on that node. Restore only the named consumers, verify their mount/read/write behavior, then advance. A Ready old pod is not completion.

Use `python3 hack/upgrade_evidence.py collect --context hpldb --candidate candidate.json > readback.json` for read-only API evidence. Collection intentionally leaves registration/readWrite/quarantine attestations incomplete. Complete them only from captured evidence. `check --candidate candidate.json --evidence readback.json` requires desired=updated=ready=available, owned ControllerRevision and control pod coverage, exact images, current generation and both Flux objects Ready. A failed check stops progression. Wait24hours after each successful cluster rollout and record start/end timestamps plus continuous health evidence before proceeding.

Native receipt kind OpenNebulaNativeQualification/v1 binds sourceCommit/sourceTree, images and canonical candidateSHA256, providerVersion and approval {operator,changeReference}. Each ordered cluster result requires result=passed, observationStartedAt/EndedAt, disposableVolumesOnly=true, readback, and tests keyed createDelete, attachDetach, attachedExpandReattach, cloneResponseLoss, cephfsRecovery, lookupFaults, quarantinePreserved, fuseDrain, detachedGrowthRejected and diskSnapshotsRejected. Each test contains result, captured commands, backendReceiptsSHA256 and immutable artifactURI. These are operator attestations supported by artifacts; JSON validation cannot prove a command ran. The protected csi-native-qualification environment must review authenticity. Local fixtures must never be submitted as native receipts.

Stable promotion uses a successful native-qualification workflow artifact at the exact source commit/tree and the protected csi-stable-promotion environment. It revalidates all three ordered24h observations and copies the qualified OCI digest without rebuilding. The binary VendorVersion deliberately retains its qualified RC value; stable is an artifact promotion, not a new binary. The stable chart packages the same source with digest-pinned defaults and a stable chart version; rendered resources must match the frozen candidate except helm.sh/chart metadata. Source or digest changes invalidate receipts. Stable publication is never an unrestricted v* tag build. The protected stable workflow publishes the stable chart index only under charts/qualified, preserving the existing shared index and its unscoped consumers. Downstream GitOps activation still requires a reviewed exact version/digest patch.

Inventory pool batching and status-write optimization are a separate follow-up branch after the first candidate, with request/write-count regression tests and benchmarks. They must not enter the first recovery candidate silently.

The publication and qualification environments must have configured required reviewers; workflows check this before proceeding. Environment names alone are insufficient approval controls. Candidate charts publish only to the isolated charts/candidates channel, which is referenced only by the three scoped suspended preparations. Stable charts publish to the isolated charts/qualified index; the existing shared chart index is unchanged. Both RC and stable images retain Docker Hub nudevco/opennebula-csi and GHCR distribution, with verified identical OCI index digests.

Candidate publication refuses an existing RC tag in either registry or an existing release before building. Unknown registry/auth responses stop publication. Re-runs must use a new RC version unless a separately reviewed reuse operation proves identical existing artifacts. Builder and runtime bases are pinned by OCI index digest; package-manager inputs still resolve during the one candidate build and are captured in its provenance. Promotion never rebuilds those inputs.
